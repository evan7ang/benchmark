## 0. 先说清三件事：术语、三条臂、为什么必须三条臂

### 0.1 术语表

第一次读这份报告的话，下面这些词是必需的：

| 术语 | 含义 |
|---|---|
| **agent hint** | 请求体里的 `agent_hint` 字段，由客户端（AISBench 的 `VLLMCustomAPI`）附加，告诉推理服务"这个请求属于哪个会话、处于什么状态"。字段全集见 [`ais_bench/benchmark/utils/agent_hint.py`](https://github.com/evan7ang/benchmark/blob/feature/agent-hint-v2/ais_bench/benchmark/utils/agent_hint.py) |
| **`cache_control`** | `agent_hint` 里的一个子字段（形状照 Anthropic 的 ephemeral cache hint）：`{"type":"ephemeral","ttl":300,"range":{"end":99999,"unit":"message"}}`。语义是"这段前缀**在会话空转期间也要留住**"。**它是本报告唯一被检验的变量** |
| **保活 / pin（钉住）** | 引擎侧收到 `cache_control` 后，把这批 KV block 从 LRU 候选里摘出来，在 TTL 内不允许被驱逐。实现见 `vllm_ascend/core/agent_hint/session_aware_manager.py` |
| **prefix cache** | vLLM 的标准前缀缓存：新请求的前缀若与历史请求逐 token 相同，就直接复用历史 KV，不再重算 prefill |
| **prefill / decode** | 一次请求的两个阶段。本实验 prompt 有 30–39 k token，**prefill 占了 TTFT 的绝大部分**，所以"命不命中缓存"直接决定 TTFT |
| **TTFT** | time to first token，首 token 延迟（客户端侧测量，含排队）。本报告的**主指标** |
| **first-turn / resume / churn** | 三类请求：`first-turn` = 会话第 1 轮（冷启动，必然全量 prefill）；`resume` = 会话第 2 轮及以后（前缀 = 上一轮全文，**命中与否就看它**）；`churn` = 与主会话无关的一次性大请求，模拟同机其它租户流量 |
| **pool / block / 超订** | 引擎 KV 池按 128 token 一块管理，共 2031 块。多会话**活跃上下文总量超过 2031 块**就叫超订，此时必然发生驱逐——**没有超订就没有可省的 prefill，两臂差异恒为 0** |
| **Φ / e / ρ / κ** | §5 的归因符号：`Φ` 受保护 token 占比、`e` 基线中被真驱逐的比例、`ρ = 1 − Δ/L` 命中还要算的新增段、`κ` 排队项 |

### 0.2 三条臂（cc / nocc / off）

三条臂**用同一份 prompt 内容**，只在两处开关上不同——这是能归因的前提：

| 臂 | 数据文件 | 模型配置（客户端开关） | hint 字段 | `cache_control` | 它隔离出什么 |
|---|---|---|---|---|---|
| **`cc`** | `_cc.jsonl` | [`ccv_on.py`](https://github.com/evan7ang/benchmark/blob/feature/agent-hint-v2/tests/agent_hint/configs/models/ccv_on.py)：`agent_hint_transport="body"`, `pass_agent_hint=True`, `agent_status_report=True` | 带 | **带**（5 条会话 × 每轮） | **hint 全开 + 保活开** → 被测方案 |
| **`nocc`** | `_nocc.jsonl` | 同上（hint 全开） | 带 | **不带** | 与 `cc` 只差 `cache_control` 一个字段 ⇒ **保活单项贡献** |
| **`off`** | `_nocc.jsonl` | [`ccv_off.py`](https://github.com/evan7ang/benchmark/blob/feature/agent-hint-v2/tests/agent_hint/configs/models/ccv_off.py)：`agent_hint_transport="none"`, `pass_agent_hint=False`, `agent_status_report=False` | **全不带** | 不带 | 关掉整套 hint ⇒ **真基线（不启用该特性）** |

命名：`cc` = **c**ache_**c**ontrol，`nocc` = **n**o **c**ache_**c**ontrol，`off` = 特性整体 off。

两个要点，避免误读：

1. **`_cc.jsonl` 与 `_nocc.jsonl` 内容逐字节相同**（3 937 261 B vs 3 931 231 B，差的 6 030 B 就是 45 个 `cache_control` 块）。会话 id、文本、长度、时间轴、churn 全都一样。
2. **`nocc` 与 `off` 用同一个数据文件**，差别只在客户端是否把 hint 字段发出去。所以 `nocc` vs `off` 量的是"hint 传输管道本身的开销"（本实验里差异在噪声内），`cc` vs `nocc` 才是"保活到底省了多少"。

**为什么必须三条臂**：只比 `cc` vs `off` 会把"传字段"和"保活"混在一起，收益说不清是谁的；只比 `cc` vs `nocc` 又不知道不启用该特性时的绝对水位。所以报告里所有结论都以**同卡同轮的 `off`/`nocc` 均值**为分母。

---

## 1. 一句话结论

在**容量超订（1.20× 池）+ 保护占比 75 % + TTL 覆盖全部 idle 间隔**的 V22 数据集上，
四条卡线（A/B/C/D）的 `cc` 臂相对同卡同轮 `off`/`nocc`：

| 指标 | 结果 |
|---|---|
| `cached_tok`（真正从缓存取出的 token） | **1.904 M vs 1.188 M，+60.3 %** |
| mean TTFT | **39 299 ms vs 50 267 ms，−21.8 %**（逐卡 −24.2 / −26.4 / −11.4 / −25.1 %） |
| p50 TTFT | **29 305 ms vs 48 643 ms，−39.8 %** |
| resume 类 mean | 13 662 vs 16 085 ms，−15.1 %（p90 在 A/D 从 68 s 降到 23 s） |
| churn 类 mean（自身从不带 hint，纯对照） | 54 587 vs 67 376 ms，**−19.0 %** |
| 代价 1 | `preemptions` 无增加；`usage mean` 仅高 0–7 pp |
| 代价 2 | 受保护会话的**首轮**（冷启 + 建钉住集）在 A/B/D 上慢 ~2×（+108 / +111 / +108 %），C 卡持平；这笔钱**已经计入**上面的 mean |

**目标（TTFT mean 降 ≥10 %）四卡全部达成**，最差一卡（C，cc 跑第一臂、引擎刚冷启）为 −11.4 %。

## 2. 数据集规格

### 2.1 文件与分发

| 项 | 值 |
|---|---|
| 生成器 | [`tests/agent_hint/data/gen_real.py`](https://github.com/evan7ang/benchmark/blob/feature/agent-hint-v2/tests/agent_hint/data/gen_real.py)（纯标准库、无依赖，全部形状参数走环境变量） |
| 变体 | `VARIANT=V22`，`SHARDS=4`（每张卡一片，避免四卡喂同一份数据互相干扰） |
| 文件 | `ccvisit_real_V22_s0_cc.jsonl` … `s3_cc.jsonl` + 同名 `_nocc.jsonl` |
| 行数 | 每片 **97 行**（8 会话 × 9 轮 = 72，churn 25） |
| 体积 | `_cc` 3 937 261 B ／ `_nocc` 3 931 231 B |
| 数据集配置 | [`configs/datasets/ccv_v22s{ A,B,C,D }{cc,nocc,off}.py`](https://github.com/evan7ang/benchmark/tree/feature/agent-hint-v2/tests/agent_hint/configs/datasets)，abbr `ccv-v22s<L><arm>` |

生成（确定性：种子固定，任何人跑出来字节一致）：

```bash
export OUT_DIR=<DATA_DIR>
export VARIANT=V22 SHARDS=4 N_SESS=8 N_PROTECT=5 TURNS=9 TURNS_BASE=30000 TURNS_MAX=39000
export GAP_LO=30 GAP_HI=240 JITTER_MAX=120 N_CHURN=25 CHURN_TOK=20000 CHURN_GAP=1.2 PROT_TTL=300 SHARED=2000
for i in 0 1 2 3; do SHARD=$i python3 gen_real.py; done
```

### 2.2 行格式（每行一个请求）

```json
{
  "question": "real-v22-s0-v03-t5",
  "max_out_len": 96,
  "timestamp": 0,
  "delay_after_ms": 41237,
  "agent_hint": {
    "session_id": "real-v22-s0-v03",
    "session": {"session_id": "...", "agent_type": "agent", "call_index": 6, "epoch": 1, "parent_session_id": "..."},
    "agent_status": {"state": "running", "state_since_ms": 1796000412370},
    "priority": {"level": 1, "reason": "critical_path"},
    "prediction": {"latency_ms": 2000, "output_tokens": 96, "remaining_calls": 3},
    "cache_control": {"type": "ephemeral", "ttl": 300, "ttl_s": 300,
                      "block_offset": 100000, "range": {"end": 99999, "unit": "message"}}
  },
  "messages": "[{\"role\":\"system\",...},{\"role\":\"user\",...}]",
  "enable_thinking": false,
  "tools": null
}
```

四个设计要点：

1. **零 pause 行**——真实 trace 里会话空转是 idle，不是请求；idle 用 `delay_after_ms` 表达。早期版本用"1.6 k token 的 pause 请求"表示空转，那是真的打到引擎上（TTFT 7.8 s，把全局均值吹高 20.8 %），而且这些请求还会刷新 LRU / 续命 TTL，悄悄给 `nocc` 的前缀保活——那是前 14 次实验"两臂命中率逐位相同"的根因。
2. **`cache_control` 只挂在 5 条受保活会话的每轮内容请求上**（45 行 = 5×9），churn 与另外 3 条会话不带。真实部署也不可能给所有会话保活（池装不下，见 2.4）。
3. **文本按 tag 种子的 xorshift 生成定长词**：同一会话同一轮在 `_cc`/`_nocc` 两份里**逐字节相同**（否则两臂内容不同、收益无法归因），不同会话/不同轮不同（避免"内容全同"造成的伪命中）。
4. **`call_index` 单调**（1 = 冷启首轮，>1 = resume），分析时按它分档，而不是按时间切。

### 2.3 形状参数

| 参数 | 值 | 设计理由 |
|---|---|---|
| 会话数 / 实例 | **8** | 单卡 2031 块，8×39 k ≈ 2 437 块 = **1.20× 池** ⇒ 全程必然驱逐 |
| 受保活会话 | **5**（62.5 %） | 5×308 = 1 523 块 = **75 % 池**；钉住的块既不可分配也不可回收（`vllm/v1/core/block_pool.py:798-808`），K→P 即死锁，实测死锁 3 次，故 5 是安全上限（6 = 1 848 块 = 91 %，临界） |
| 轮数 | **9** | 起点即长上下文，减少"爬升段无压力"的摊薄（V21 的教训） |
| 上下文起点 / 终点 | **30 000 → 39 462 tok**（实测 prompt_tokens 最大 **39 180**） | 模型硬顶 40 960，>40 k 必须换 YaRN 配置副本（`rope_scaling: yarn, factor 4` + `--max-model-len 81920`） |
| 轮间 idle | 30–240 s（实测客户端视角 p50 **83 s**、max **163 s**） | 真实 agent 一轮之间是人在看/工具在跑；全部 < ttl 300 s |
| 起跑抖动 | 0–120 s | 把 8 路 30 k prefill 错开，否则全撞在一起 |
| churn | 25 × 20 k，间隔 ~56 s | 提供 LRU 翻转动力，同时把瞬时到达率压在服务率之下 |
| `cache_control.ttl` | 300 s | ≥ 最大 idle 间隔，保护在整个空转期内有效 |
| 共享 system 前缀 | 2 000 tok | 模拟同一 agent 产品的公共系统提示（两臂都白拿，不构成差异） |

### 2.4 画像（分片 0 实测，其余三片同构）

| 类别 | 行数 | token（最小 / 均值 / 中位 / 最大） | 合计 |
|---|---|---|---|
| 首轮 | 8 | 27 323（起点固定，8 行同长） | 0.219 M |
| resume | 64 | 28 534 / 32 631 / 32 772 / 35 876 | 2.088 M |
| churn | 25 | 18 200 恒定 | 0.455 M |
| **合计** | **97** | 名义 2.76 M → **实测 3.02 M** | 均值 31 131、p50 32 635、**max 39 180** |

- **上下文逐轮累加达标**：30 000 → 39 462 tok，实测最大 prompt 39 180 token，压在模型硬顶之下。
- **idle 比例符合真实逻辑**：同会话相邻两轮间隔实测 p50 **83 s**、max **163 s**、min 13 s，**超过 ttl 300 s 的一次都没有**——ttl 覆盖整个空转期，这是 `cc` 能命中的物理前提。
- **池压力**：turn1 合计 8×30 k = **1 875 块（92 % 池）**，末轮 **2 437 块（1.20× 池）**；保护固定占 1 523 块（75 %），余 508 块给 3 条未保护会话 + churn 抢。
- **到达率 0.106–0.127 req/s**，轨迹跨度 739–912 s。
- **受保护会话承载 Φ = 47 % 的 prompt token**（5×(27.3 k + 8×32.6 k) = 1.44 M / 3.02 M）——收益的物理上限。

### 2.5 相对 V21 只改三处（唯一变量）

| 项 | V21 | V22 |
|---|---|---|
| 会话起点 | 5 000 tok，+3 800/轮 | **30 000 tok，+1 125/轮** |
| 起跑抖动 / 轮间隔 | 0–6 s / 15–240 s | **0–120 s / 30–240 s** |
| churn | 30 × 20 k / ~50 s | **25 × 20 k / ~56 s** |

V21 的失败原因：8 路会话中段只有 312 块 ≪ 2031，**只有轨迹尾部才超订**，`e` 被摊薄到约 15 %，于是 cc 只赢 7–9 %。

## 3. 实验步骤

### 3.1 部署拓扑

| 卡 | 引擎端口 | 数据集分片 | 臂序（轮转） |
|---|---|---|---|
| card0 | 18220 | s0 (A) | off → nocc → cc |
| card1 | 18230 | s1 (B) | nocc → cc → off |
| card3 | 18260 | s2 (C) | cc → off → nocc |
| card7 | 18250 | s3 (D) | off → cc → nocc |

引擎启动参数（12 臂完全一致）：

```bash
vllm serve <MODEL_PATH>/Qwen3-8B --served-model-name kvh --port <PORT> \
  --tensor-parallel-size 1 --max-model-len 40960 --gpu-memory-utilization 0.9 \
  --enforce-eager --enable-prefix-caching \
  --num-gpu-blocks-override 2031
```

**臂序为什么要轮转**：同一配置重启之间的实例漂移实测达 +18 % / −27 %（同参两卡 2335.8 ms vs 2127.5 ms = 9.4 %）。若四卡统一 `off→nocc→cc`，"第三个臂总是更快"就会被误读成 cc 的收益。轮转后每种臂至少在两个位置上各出现一次，位置项在合并均值里自消。V21 里 C 卡（cc 跑第一）只拿到 −1.8 %、A/D（cc 跑第二三）拿到 −9.0/−9.6 %，就是这个效应的直接证据。

### 3.2 单臂流程（12 次重复）

1. **冷启隔离**（[`scripts/cleanlane.sh`](https://github.com/evan7ang/benchmark/blob/feature/agent-hint-v2/tests/agent_hint/scripts/cleanlane.sh)）：对该端口上的 `bin/vllm serve` 发 SIGTERM，轮询等退出（不退出才 `pkill -9`），重新拉起并等 `/health` 通过。
   **必须重启而不是清缓存**：`POST /reset_prefix_cache` 在本 build 返回 `{"success":false}`；跳过重启会让上一臂的前缀白送命中（实测 hot 99.4994 % vs cold 94.3862 %）。
2. **核对容量**：每臂 `obs-before.json` 记录 `num_gpu_blocks="2031"`、`kv_cache_size_tokens="259968"`，12/12 一致（引擎启动行里的 `num_gpu_blocks=2237` 是 NPU 自算值，override 后真正的池是 2031）。
3. **回放**（[`scripts/run_arm.sh`](https://github.com/evan7ang/benchmark/blob/feature/agent-hint-v2/tests/agent_hint/scripts/run_arm.sh)）：起一个客户端容器（每臂新建），用 `ais_bench --config-dir <CFG> --models ccv_<arm> --datasets ccv_<v22sL><arm> --mode perf --num-warmups 0`，按 `delay_after_ms` 逐行发请求。
4. **采样**：请求前后各抓一次引擎 `/metrics`（`obs-before/after.json`），运行中每 ~2 s 采 `pool.csv`（`kv_cache_usage_perc`、`waiting`、`num_requests_running`）。
5. **落记录**：`recs.json` 逐请求 `ttft_ms / total_ms / prompt_tokens / out_tokens / call_index / session / state`。

### 3.3 计时与规模

- 12 臂全部完成：**10:53 – 11:16**（约 23 min 墙钟），单臂 4.5–6 min，引擎重启 ~1.7 min，四卡并行。
- 每臂工作量：3.02 M prompt token（三臂相同）。

### 3.4 指标口径（三个坑，必须按这个读）

| 指标 | 能不能跨臂比 | 说明 |
|---|---|---|
| `vllm:prefix_cache_queries_total` | **不能** | `cc` 臂被放大 **3.3×**（37–41 M vs 10.4 M），保护路径每请求都重过一遍块注册/查询。所以 cc 的"命中率 76–94 %"与 nocc 的"51–57 %"不是同一分母 |
| `prompt_tokens_cached_total`（本文 `cached_tok`） | **能** | 真正从缓存取出的 token 数，三臂分母相同（3.02 M） |
| `vllm:kv_cache_usage_perc` | 只做"保护是否占住"的证据 | 统计的是**已占用块（pinned + 在飞）**，不是缓存存量，**不能**当命中率或驱逐率 |
| `preemptions_total` / `waiting` | 压力证据 | 判断"收益有没有转嫁给别人" |
| 延迟 | 客户端 `ttft_ms` | 分档：resume（`-v` 且 `call_index≥2`）/ 首轮（`call_index=1`）/ churn（`-c`） |

| resume mean | 13 662 ms | 16 085 ms | −15.1 % |
| 首轮 mean（8 行/臂，见 4.4） | 54 372 ms | 30 913 ms | **+75.9 %（更慢）** |
| churn mean | 54 587 ms | 67 376 ms | **−19.0 %** |
| usage mean | 64.1–71.5 % | 63.7–65.3 % | 持平~略高 |
| preemptions | 0 / 0 / 1 / 0 | 0 / 0 / 1 / 1 | 无增加 |

### 4.4 分布形态

- 基线（off/nocc）的 resume 是**双峰**：p50 ≈ 10 s（全量 34 k 重算）+ 尾部 p90 ≈ 26–70 s（重算又撞上别人的 prefill，排队放大）。
- `cc` 把受保护会话整段搬到低峰：p50 8.9–10.4 s 基本不变（因为混着 3/8 未保护会话），但 **p90 在 A/D 从 68 s 掉到 23 s**（A 卡 68 721 → 23 585 ms，−66 %）。
- B/C 卡基线 p90 本来就不高（26 s），cc 的 p90 反而略高（29.9 / 35.6 s）——这两卡的非 cc 臂位置更"幸运"，属位置噪声，故结论以 mean + p50 + cached_tok 三者互证。
- **首轮形态（代价项，见 5.4）**：A/B/D 三张卡的 cc 臂里，首轮呈"**5 慢 3 快**"的整齐分裂——正好是 N_PROTECT=5：受保护会话的首轮 58–103 s，未受保护的 3 条 6.8–20.8 s（A 卡 `[72.3, 58.4, 62.9, 20.8, 67.5, 13.8, 102.9, 6.8]`）。基线臂没有这种分裂。所以保护是"先付首轮、后收 resume"。

## 5. 归因分析

### 5.1 定量式子

设

- `Φ` = 受保护会话承载的 prompt token 占比 = **0.47**（1.44 M / 3.02 M）
- `e` = 基线中这些 token 真被驱逐的比例 = **≈ 0.52**（由 `cached_tok` 差 0.717 M ÷ 受保护 resume 需求 1.42 M 反算）
- `ρ` = 1 − Δ/L = 1 − 1 125/34 000 = **0.97**（命中仍要算新增的 Δ 段）
- `κ` = 排队项

```
Φ·e·ρ = 0.47 × 0.52 × 0.97 = 0.237   （23.7 % 的 prompt token 从"必算"变成"命中"）
实测 mean TTFT 降幅 = 0.218
传递比 = 0.218 / 0.237 ≈ 0.92
```

### 5.2 为什么几乎 1:1（κ 不是噪声）

`waiting max = 32`、`usage max ≈ 99.5 %` ⇒ 两臂处在**同一条饱和带**，瓶颈是引擎的批吞吐 B，单请求 `TTFT ≈ 排在前面的工作量 / B`，于是 **mean TTFT ∝ 总 prompt token**。cc 只是少算了 23.7 % 的 token，整条队列就短 23.7 %。

**关键判断**：κ 在饱和态下是两臂的**共因**，不对差值打折。先前担心的"排队淹没收益"只在"一臂饱和、一臂不饱和"的错配下成立——那种对照本身不公平，不是数据集的问题。

### 5.3 三条独立佐证（收益是系统级的）

1. **churn 类也降 19 %**：它自身从不带 `cache_control`，唯一解释是"别人少算了，队列短了"。
2. **`preemptions` 没升、`usage mean` 仅高 0–7 pp**：收益没有转嫁给其它会话。
3. **两条卡线的 resume p90 从 68 s 掉到 23 s**：尾部是"重算又撞上别人的 prefill"，只有前缀真被留住才会整体塌下来。

### 5.4 代价与边界（诚实记账）

- `cc` 的 `queries` 被放大 3.3×：块级注册/查询是真实开销，这也是"少算 39.1 % 预填 token 只换来 21.8 % 延迟"差额的一部分；另一部分是请求侧 JSON / 分词 / 调度开销只与总 token 成正比，不随命中减少。
- **保活上限**：5/8 = 75 % 是安全线；6 路 = 91 % 已接近 `block_pool` 的硬边界（实测死锁 3 次，`K + in-flight > 0.9 × P` 时 pinned 区会把可分配区吃空）。
- **C 卡只有 −11.4 %**：该臂 cc 跑第一（引擎冷启、`waiting=32` 最深），是最保守的一次测量，也说明**收益对实例状态的敏感度约 ±13 pp**——所以必须靠臂序轮转 + 同卡对比，不能跨卡比。
- **上下文天花板 39.2 k**：更大上下文需要 YaRN 配置副本，本轮未做。
- **首轮要预付**（本轮新发现的代价，已计入 mean）：A/B/D 上受保护会话的首轮从 24–33 s 涨到 50–69 s（+108 / +111 / +108 %），C 卡持平。形态是"5 慢 3 快"，与 `N_PROTECT=5` 完全对齐，说明成本落在**建钉住集的那一次请求**上，而不是泛泛的拥塞。最可能的机制是保护侧准入：`K + in-flight` 一旦逼近 `0.9P`，受保护请求要等池里腾出位置才被放行（就是我们踩过 3 次死锁的那条不等式），而 t≈0–120 s 正是 8 路冷启同时要块的时刻。**待验证**：单卡只放 1 条受保护会话，看这笔惩罚是否随 `N_PROTECT` 线性增长。

---

## 6. 结论与下一步

**结论**：V22 是第一个"上下文逐轮累加到 39 k + 单实例 8 路会话超订 1.20× + 零 pause + TTL 覆盖全部 idle"的数据集。在这一形状下，agent-hint 保活**四卡全部拿到 ≥10 % 的 mean TTFT 收益（合并 −21.8 %，最差卡 −11.4 %）**，`cached_tok` +60 %、p50 −39.8 %、p90 在两条卡线上 −66 %，且代价面干净（无新增抢占、无明显占位上升）。

**下一步**：

1. **V23（容量重、吞吐轻）**：8 会话/5 保活、30 k→39 k、6 轮、轮间隔 60–180 s、抖动 0–240 s、churn 18×20 k —— 目标 `waiting ≈ 0`，把 `κ` 彻底解耦，检验 `Φ·e·ρ` 在非饱和态是否仍成立，并分离"命中 ≈1–2 s / 未命中 ≈10 s"的单请求量级。
2. **TTL 扫**（1 / 60 / 300 / 1 800 s）：确认收益对 `ttl` 的敏感性（`ρ` 决定下限）。
3. **池扫**（2031 / 1 800 / 1 500）：验证 75 % 保护占比这条边界。
4. **微基准**（同一 39 k prompt 连发两次）：直接量"命中 vs 未命中"的 TTFT 差，校准 5.1 的传递比。
5. **首轮代价定位**：`N_PROTECT` = 1 / 3 / 5 各跑一次，看 5.4 那笔预付款是否线性；若线性，部署时就该给"新建会话"留一段不保护窗口（首轮不打 `cache_control`，第二轮再打），把准入等待挪出关键路径。
6. **部署侧**：8 会话/卡已打满单实例（`waiting max 32`）⇒ 32 并发会话需**每卡 2 实例 + 网关 sticky**；>40 k 需 YaRN；再不够上 KV offload。
